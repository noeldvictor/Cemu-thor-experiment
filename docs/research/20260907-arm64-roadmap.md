# ARM64 performance roadmap for the Thor (2026-09-07)

Decisions recorded on 2026-09-07, after the upstream sync of the same day:

- **Scope: all four remaining projects**, in the order below.
- **Benchmark: the Star Fox Zero loading phase**, three runs per build, in-place A/B on the
  same device. CPU ticks over 20 s from `/proc/<pid>/stat` fields 14+15, sampled 8 s after
  launch, plus Init-to-Run-title time from `log.txt`. Gameplay FPS is vsync-capped and does
  not detect CPU changes; see AGENTS.md "Measured Baseline".
- **Build policy: aggressive defaults.** The Android release build assumes Snapdragon 8 Gen 2
  class hardware (`CEMU_AARCH64_ASSUME_SNAPDRAGON_8GEN2`, `-march=armv8.2-a+lse+dotprod+fp16+rcpc`,
  `-mtune=cortex-a710`). It will not run on pre-ARMv8.2 devices. Fast-math stays off until a
  per-game regression pass exists.

The RPCS3-derived list (`20260820-rpcs3-arm64-optimizations-for-cemu.md`) is exhausted:
feature detection, the lock-free clock, NEON texture hash, the one-instruction shifts and the
idle-core fix all landed and were measured, and the CP spin-count retune was measured worse
and reverted. What is left is structural work, which is why it needed a decision.

## 0. Build for the hardware (done this session, measured below)

Inline LSE atomics for every `std::atomic` read-modify-write instead of the outline-atomics
call plus branch. Cheap to do, whole-binary effect. Measured with the A/B protocol above;
result recorded in AGENTS.md "Measured Baseline".

## 1. Persistent recompiler cache

**Why first.** Cemu recompiles every guest function on first execution and keeps nothing
across runs. On the loading phase, roughly half of the samples are in recompiled guest code
and the rest is host overhead, of which recompilation itself is a fixed tax paid every boot
and every new scene. AGENTS.md already calls a disk-backed cache "the more valuable project"
and the prerequisite for any heavier codegen. It also removes the scene-load stutter that a
handheld user actually feels.

**Step 1, measure the ceiling (device, one session).** Profile the loading phase with
simpleperf and sum the samples under `PPCRecompiler_*`, the IML passes and
`BackendAArch64` emission. That number is the maximum a cache can save on loading; if it is
under about 10% of samples, stop here and reorder the roadmap.

**Step 2, design.** Key: title id + RPX/RPL hash + function address + a hash of the
function's PPC bytes (graphic-pack patches and the Star Fox tiny-wrapper inliner rewrite
guest code before recompilation, so the code bytes must be in the key). Value: the emitted
AArch64 code plus a relocation list. The backend binds known HLE function pointers and
absolute host addresses at compile time (`BackendAArch64.cpp`, known-call wrapper, the
`PPC_REC_INSTANCE_REG`/`MEM_BASE_REG`/`HCPU_REG` bases are register-relative and need no
relocation), so every embedded host pointer needs a relocation entry or must move to an
indirection table. Store under the app files directory next to the shader cache, one file per
title, append-only with an index, so a crash mid-write loses only the tail.

**Step 3, load path.** On title start read the index, `mmap` the code file into the
recompiler's executable region, apply relocations, and register the function ranges the same
way a fresh compile does. Validate with a checksum per entry; a mismatch falls back to
recompiling that function.

**Step 4, measure.** Startup time and loading-phase ticks, cold cache vs warm cache. Then
the hot-block profiler dump before and after to confirm the executed code is identical.

## 2. Adreno render-pass and barrier work

**Benchmark caveat.** The loading phase cannot measure GPU work. Use a fixed in-mission
Star Fox scene at the 60 Hz cap and read GPU busy time from KGSL
(`/sys/class/kgsl/kgsl-3d0/gpubusy`) over 20 s, three runs; the AGENTS.md baseline already
notes the GPU sits around 15% busy in reachable scenes, so the metric is "busy percentage
for identical output", not FPS.

**Candidates, from Qualcomm's guide in `docs/reference/adreno/mobile_best_practices.txt`:**
- Render-pass merging and `LOAD_OP_DONT_CARE`/`STORE_OP_DONT_CARE` wherever Latte's
  render-target tracking already knows the contents are dead; every `LOAD_OP_LOAD` is a
  GMEM resolve on a tiler.
- The inter-renderpass barrier rework in upstream PR `#1759` (draft, stale since April).
  Barriers between passes force a flush of the binning pipeline; this fork's
  "accurate barriers" toggle exists because the current code is coarse.
- `VK_EXT_attachment_feedback_loop` (now on the branch) replaces the copy-to-self path;
  confirm Turnip advertises it and that it is taken in the Star Fox scene.
- Depth-only passes and LRZ: keep depth formats and clears in the shapes the guide lists.
- Swapchain: the log shows "Can't find immediate present mode" on Turnip; check whether
  mailbox is offered and whether the dual-screen present pair could use it.

## 3. Recompiler codegen from the core manuals

Per-item work measured with the loading-phase ticks and the hot-block profiler. Candidates,
each checked against the Cortex-X3 / A715 / A710 / A510 software optimisation guides in
`docs/reference/arm/`:
- `ldp`/`stp` for adjacent guest-context loads and stores (the SWOGs give paired
  load/store the same latency as single).
- Instruction fusion (X3 and A715 section 4.11): `CMP`/`CMN`/`TST` immediately followed by
  `B.cond`. The flags-based branch fusion already exploits this; audit the emitter for
  places where an unrelated instruction is scheduled between the compare and the branch.
- Zero-latency `MOV` (X3 4.12): register-to-register moves that the rename stage
  eliminates; prefer them over `ORR`-based copies.
- `cbz`/`cbnz`/`tbz`/`tbnz` for compare-with-zero and single-bit tests instead of
  `cmp`+`b.cond`.
- `csel` chains versus a short branch: the guides list `csel` at 1 cycle but a chain of
  dependent `csel` serialises; profile the paired-single clamp paths first.
- **Thread placement on the A510s.** The three little cores are in-order and roughly a
  third of the X3's throughput. ADPF hints are meant to keep the scheduler threads off
  them; verify with `/proc/<pid>/task/*/stat` field 39 during the loading phase. If a
  guest core thread is landing on cpu0-2, that is worth more than any emitter change.

## 4. Correctness: NaN differential tests

Device-free. Pin Espresso `fctiwz` (NaN -> `0x80000000`) and the `psq_st` quantisation of
NaN/Inf (positive saturation value per the Gekko manual) with cpu-tests, then fix both
backends together. Today the ARM backend returns 0 for `fctiwz(NaN)` and the two backends
give three different answers for a quantised NaN store. No game has been shown to hit
either, which is why this is last, but the tests must exist before item 3 touches the
paired-single paths.
